# Provenance — test/firmware-rehosting/robot-stm32/

Rehosts a real **self-balancing-robot controller** firmware for an
**STM32F103 (Cortex-M3, NUCLEO-F103RB)** from the P2IM real-firmware
dataset, using the auto-modeling path (AutoPeripheral). It is the second
real device demonstrating that the auto-modeler generalizes beyond the
GRBL CNC case.

**The firmware binary is not shipped here.** `Robot.elf`, `Robot.bin`,
and `robot_addrs.yaml` are regenerated by `extract.sh` from the
[`RiS3-Lab/p2im-real_firmware@d4c7456`](https://github.com/RiS3-Lab/p2im-real_firmware/tree/d4c7456574ce2c2ed038e6f14fea8e3142b3c1f7)
dataset's prebuilt, unstripped `binary/Robot` ELF.

| Setting | Value |
|---------|-------|
| MCU     | STM32F103 (Cortex-M3), STM32 HAL |
| Flash   | 0x08000000 (128 KB) |
| RAM     | 0x20000000 (20 KB) |
| Console | USART data register, auto-discovered by AutoPeripheral |

## Licensing

This directory ships only configuration + scripts — no firmware source or
binary. The P2IM dataset's prebuilt binaries are AFL-instrumented (an
`aflCall()` stub issuing `svc #0x3f`); the unicorn backend's `skip_svc`
steps over it.

## What it demonstrates

The robot firmware is a control loop, not a console app, so unlike GRBL it
emits little text. The test asserts the auto-modeling *mechanisms* fire:
the firmware boots, the AutoPeripheral auto-discovers a UART data register
and breaks an MMIO spin-wait — with no UART/clock-wait intercept — proving
the stack is not CNC-specific.
